Task 1 — LoRA fine-tuning

My notes: what I built, why I built it that way, and what broke

Assignment: tndrr AI/ML internship  ·  Model: Qwen2.5-0.5B-Instruct  ·  Hardware: free Colab Tesla T4, 15.6 GB  ·  Data: Banking77, 77 intents  ·  Result: 0.0% → 94.0% held-out accuracy

1. What the task asked for, and what I decided it really meant

The brief said: fine-tune a model ≤1.5B parameters on a narrow task, then show base vs fine-tuned on at least 50 held-out examples with a clear metric, explain my LoRA settings, show 3 failures, and do a memory calculation for 7B.

The phrase that shaped every decision was “tests your understanding, not just whether you can get code to run.” A fine-tune that scores well but that I cannot explain is worthless here, and they explicitly said they will walk me through the code live. So I optimised for a pipeline small enough that I can defend every line, not for a large model or a clever dataset.

The task I chose

A bank support ticket in plain English → exactly one JSON object: 

{"category": "card_arrival"}

Boxed into 77 legal values from Banking77, a real public dataset of 10,003 labelled customer queries. I picked it for four reasons:

  • It is real data, not something I generated. If I had written my own templated dataset, the evaluation would only prove that the model learned my template. Banking77 was collected from actual support chats, so the errors are real errors.
  • The output space is closed. 77 known strings means accuracy is exact-match, not a fuzzy score I would have to justify.
  • The classes genuinely overlap — card_arrival vs card_delivery_estimate, several *_fee_charged variants. So the number is not free; 94% is not automatic.
  • A 0.5B model can actually learn it. If I had used a 10-class toy problem, the base model might already score well and the fine-tune would show nothing.
Why 0.5B and not 1.5B? The brief allows up to 1.5B, but a 0.5B trains in about 7 minutes on a free T4 and I can run it three or four times in an afternoon. That iteration speed is worth more than the extra capacity, because I can measure and fix problems instead of guessing. If the task had needed more reasoning — multi-step tool use, say — I would have gone to 1.5B.

2. How the pipeline actually works

Five stages. This is the version I would draw on a whiteboard.

2.1 Data split

SplitSizePurpose
Train9,703gradient updates
Dev300carved out of train (seed 0), used only to watch progress
Held-out test300first 300 rows of the official test split, never touched during training

The dev set exists so that “is it learning?” and “is it generalising?” are two separate questions. The test set is the one I report, and I only look at it after training is finished.

2.2 Prompt and target

I use the model’s own chat template, with a short system message that defines the output shape, then the ticket as the user turn. The target is the compact form of the JSON with no spaces: 

system: You are a bank support ticket router. Reply with JSON only, in exactly this form: {"category": "<label>"}
user:   I am still waiting on my card?
assistant: {"category":"card_arrival"}

No spaces in the target is deliberate. It makes “byte-exact match” a real test: if the model learns the format from the data, it reproduces the exact string; if it is guessing, it emits spaces and fails.

2.3 Loss masking

The prompt tokens are set to -100 and the answer tokens keep their ids. Cross-entropy ignores -100, so the model is only trained on the answer.

Why: if I trained on the whole sequence, most of the gradient would go into predicting the user’s question — which is random text I do not want the model to learn to produce. Masking puts 100% of the learning signal on “given this ticket, what is the label”.

2.4 LoRA

Instead of updating the 503M original weights, LoRA freezes them and inserts two small matrices into each linear layer. For a weight matrix W of shape d×k, the update is W + BA, where B is d×r and A is r×k. With r=16 that is orders of magnitude fewer parameters, and at inference you can merge BA back into W so there is no speed penalty.

In my run the adapter is 8,798,208 parameters out of 502,830,976 — 1.75%. That is the whole point: 1.75% of the weights move, the rest stay frozen in fp16 with no gradients and no optimizer state.

2.5 Training loop and evaluation

Hand-written loop over transformers + peft: forward with fp16 autocast, scaled backward, gradient clip at 1.0, AdamW step, cosine schedule. I did not use TRL’s SFTTrainer on purpose — see §6 — because a loop I wrote is a loop I can explain line by line.

Evaluation is greedy decoding (do_sample=False) so results are deterministic and two models are compared under identical conditions. Three metrics:

MetricDefinitionWhat it catches
valid_jsonoutput parses and has a string categoryformat failures, rambling
category_accuracyparsed label equals the gold labelthe real question
strict_json_exactraw string byte-identical to the gold stringwhether the format was learned, not just the label

Why the 0.0% baseline is real and not a bug

My first reaction to 0.0% was that my evaluation was broken. So I printed the base model’s raw outputs: 

{"category": "bank"}
{"category": "pending"}
{"category": "受理"}

It produces well-formed JSON and has no idea what the label vocabulary is — it fills the slot with a plausible banking word, sometimes in the wrong language. That is why valid_json is 99.7% while accuracy is zero.

To make sure I was not strawmanning the base model, I ran a second baseline with all 77 labels pasted into the prompt. It reached 21%, and JSON validity actually fell to 63.7% because the long prompt made the model start talking around the answer. So the fine-tune is buying task knowledge, not formatting skill — and the gain is 21% → 94%, not 0% → 94%.

Two runs, two numbers. An identical earlier run with maxlen=64 scored 95.3% on the same 300 examples. I report the 128-token run at 94.0% because it is the cleaner setup, and I state the difference rather than quietly keeping the better-looking number. At n=300 the 95% confidence interval is about ±2.7 pp, so this gap is noise, not a real regression.

4. What broke, and how I fixed it

None of this went in one pass. These are the five things that actually cost time.

4.1 The MASSIVE dataset would not load

I originally wanted the Amazon MASSIVE dataset, because its output is richer: domain + intent + slots, which is closer to a real “request → structured JSON” task. 

RuntimeError: Dataset scripts are no longer supported, but found massive.py

datasets 4.x removed script-based datasets, and MASSIVE ships as a loading script. I tried the parquet export API instead; it returned HTTP 500. So I switched to Banking77, which loads from parquet natively and is equally real. Cost: one less output field. Benefit: I did not burn the afternoon fighting a loader.

4.2 My first %%writefile silently wrote nothing

%%writefile /content/task1/train.py needs the directory to exist. It does not create it, and it does not obviously complain inside the notebook. I discovered it with a two-line existence check that returned dir: False | train.py: False, created the folder, and re-ran the cell.

Lesson: after any file-writing cell, verify the file exists. That one check saved an hour of debugging a “missing module”.

4.3 torchao broke PEFT’s LoRA dispatcher

ImportError: Found an incompatible version of torchao.
Found version 0.10.0, but only versions above 0.16.0 are supported

Colab ships torchao 0.10; PEFT 0.21 probes it when building LoRA layers and raises instead of falling back. I do not use torchao at all, so the fix was to remove it: pip uninstall -y torchao. The smoke test then passed.

4.4 I wrote eval.py but never executed the cell

The evaluation died with python3: can't open file '/content/task1/eval.py'. The writefile cell had been created but never run, so the file did not exist. Fixed by running the cell, then checking wc -l and parsing the file with ast before launching anything.

4.5 The real bug: 64 tokens was silently cutting my system prompt

I measured prompt+answer lengths instead of guessing:

p50p95p99maxrows > 64
57728812312.8%

My code keeps the last 64 prompt tokens and then appends the full answer. For 12.8% of rows that meant the system message was truncated away during training — but at inference the system message is always present. That is a train/inference mismatch, and it is exactly the kind of thing an interviewer finds by reading the code. I retrained at maxlen=128, which covers the observed maximum of 123.

This is the fix I am most willing to be asked about, because it came from a measurement rather than a hunch: p95 was 72 tokens, 72 > 64, therefore the cap was clipping real rows.

5. LoRA settings, and the alternative for each one

SettingValueWhy this, and not the obvious alternative
r16r=8 is usually enough to learn a format. Here the model has to learn 77 new label semantics, so I doubled capacity. Cost is still 1.75% of params. r=32 would have been 3.4% for a task this narrow.
alpha32α = 2r is the common convention: effective scale α/r = 2 without touching the learning rate. I did not tune it separately, and I say so.
dropout0.059.7k rows × 2 epochs is small. Light regularisation; 0.1 slowed convergence for no measurable gain.
targetsq,k,v,o + gate,up,downAttention-only adapters learn output style well but struggle when the mapping lives in the MLP blocks. All-linear costs 8.8M params — negligible — and removes a variable.
lr2e-4LoRA tolerates more than full FT. 1e-3 was the risky end at effective batch 32; 1e-4 would need more epochs.
schedulecosine, 3% warmupWarmup avoids a destructive first few steps; cosine decays into the end so the final weights are not left at a high LR.
epochs2Loss 0.016 and dev 90% after two. A third epoch on 9.7k rows mostly memorises.
batch16 × accum 2Fits the T4 with headroom (9.12 GB peak). Effective 32 stabilises LoRA gradients.
precisionfp16 + GradScalerThe T4 is Turing: no native bf16. fp16 with loss scaling is the correct choice there.

6. Approaches I considered and rejected

Full fine-tuning instead of LoRA

Rejected on memory and on risk. Full FT needs the weights, the gradients, an fp32 master copy and two Adam moments: about 16 bytes per parameter, so 7B would be ~112 GB of state before activations. Even at 0.5B it is roughly 8 GB of state, and every weight is a moving part. LoRA also makes the deliverable inspectable: an 8.8M adapter next to a 503M frozen base.

QLoRA instead of LoRA

Rejected because it solves a problem I did not have. At 0.5B, fp16 weights are about 1 GB; the T4 has 15.6 GB. 4-bit would save under a gigabyte, add dequantisation work to every forward pass, and introduce quantisation noise into a comparison I want to be clean. QLoRA is the right answer when the model does not fit — which is exactly the 7B case in my memory calculation, and that is where I use it.

TRL’s SFTTrainer instead of a hand-written loop

Rejected on purpose. SFTTrainer hides the loss masking, the collator and the scheduler behind arguments. That is great when you are shipping; it is bad when you have to explain where the gradient comes from. Writing the loop meant I had to make the -100 mask explicit, and that is now something I can defend.

A synthetic templated dataset instead of Banking77

Rejected because it makes the result meaningless. If I generate the data from ten templates, the model learns the templates and 99% accuracy proves nothing about language. It also would not produce honest failure cases — which is a graded part of the task.

Few-shot prompting instead of fine-tuning

This is the baseline, not an alternative I skipped: with all 77 labels in the prompt the base model reaches 21%. That number is why the fine-tune exists. With a 0.5B model, 77 labels plus few-shot examples would not even fit comfortably in context.

Reporting the dev number, or the better of two runs

Rejected because it is dishonest and because they will ask. Dev is 90.3%, test is 94.0%, and an earlier run was 95.3%. I report test, and I mention the other run and the noise band. Choosing the flattering number is how you fail a walkthrough.

A bigger model, or a harder task

Considered and rejected for this deadline. 1.5B would roughly triple training time for a task a 0.5B already solves at 94%. Multi-field JSON (intent + slots) would be a better demo of structure but adds a span-extraction metric and more failure modes, and I would rather ship one clean, explainable result than a richer one I cannot fully defend.

9. Questions I expect, and the short answer

If they ask…The answer
Why LoRA and not full fine-tuning? Full FT is ~16 bytes/param of state — about 112 GB for 7B — and touches every weight. LoRA trains 1.75% and keeps the base frozen and inspectable. At this model size full FT would have fit, but it buys nothing for a task the adapter already solves.
Why r=16? The task needs new label semantics across 77 overlapping classes, not just a new output style. r=8 is the usual starting point for style adaptation; 16 doubled capacity for 1.75% of params. r=32 would have been 3.4% with no evidence it was needed.
Why alpha=32? α = 2r is the convention; effective scale α/r = 2. I did not tune it separately — I would rather say that than invent a justification.
Why mask the prompt in the loss? So 100% of the gradient goes into “ticket → label”. Otherwise most of the learning signal is spent predicting the user’s question, which is random text.
Why is the baseline 0%? It is not broken: the base model emits valid JSON but has no label vocabulary, so it writes "bank" or "pending". With the 77 labels in the prompt it gets 21%, which is the fairer comparison.
Why 300 test examples? Enough for a ±2.7 pp interval at 95% confidence, which separates 21% from 94% decisively.
Why did the second run score lower? 95.3% → 94.0% is 4 examples out of 300, i.e. inside the noise band. The 128-token run is the cleaner setup, so it is the one I report.
What would you do with more time? Minimal-pair contrastive data for the confusable families (card timing, fee charges), label descriptions in the system prompt, and a kNN few-shot baseline. Then a rank sweep at n=1,000 test examples to make small differences measurable.

10. What I would tell them is still weak

  • One seed per configuration. I have one run at r=16, so I cannot claim a rank sweep. I can claim the pipeline is reproducible: the same script and data give the same result.
  • 300 test examples. Enough to rank these three settings, not enough to claim a precise state of the art. The published Banking77 numbers use all 3,080.
  • No slot extraction. The output is one field. A richer schema would show more, but it also adds a span metric I would need to justify.
  • Some gold labels are arguable. A handful of the 18 errors are boundary cases inside the *_fee_charged family. I say so in the report rather than hiding it, but it is a real caveat on the 94%.
