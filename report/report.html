Task 1 — LoRA intent router

I fine-tuned Qwen2.5-0.5B-Instruct to turn a customer-support message into strict JSON, {"category": "<one of 77>"}, on Banking77. I picked a 0.5B model because the task is narrow and short — the p95 of prompt-plus-answer is 72 tokens — so a small model keeps the cost/accuracy trade-off visible instead of hiding it behind scale. Split: 9,703 train, 300 dev (never trained on), 300 held-out from the official test split.

The bug worth talking about. My first run used maxlen 64. The tokenizer keeps the last 64 tokens, so on 12.8% of rows it silently dropped the system prompt and the label list — the model was being asked to answer a question it could no longer see. The token-length histogram (p95 = 72, max = 123) said 128 was the right ceiling, so I retrained. The 128 run is the one I report: 606 steps, 435.6 s, 9.12 GB peak on a Colab T4.

The base model's 0.0% is not a parsing artefact: it returns perfectly valid JSON with invented labels ("bank", "pending", "受理"). Give it the label list and it can pick one, but validity collapses to 63.7% because it starts explaining itself. The adapter is what makes the output a contract rather than a suggestion.

Three failures, and why they happen

  • Sibling intents — 5 of 18. Mostly card_arrival → card_delivery_estimate (4 cases). "When will I get my card?" is genuinely both; the model picks the more literal phrasing rather than the dataset's convention.
  • Domain boundary — 3 of 18. fiat_currency_support → exchange_via_app. "Do you support USD?" is about support, not conversion. The model reads the currency, not the verb.
  • One word flips it — 1 of 18. "My account was charged for a withdraw I tried to make that was decline." → declined_cash_withdrawal instead of pending_cash_withdrawal. The cue is real but points the wrong way.

Full list and confusion counts: task1-lora/results/failures.json. I report the 94.0% run, not my earlier 95.3% at maxlen 64 — that run had the truncation bug, and +1.3 pp is inside the ±2.7 pp binomial noise at n=300.

For 7B, r=16 on all seven projections is 40.4M trainable parameters (0.58%). Full FT needs the weights, an equally sized gradient buffer, and Adam's two fp32 moments (8 bytes/param), so it does not fit on a 24 GB card — it needs 2×80 GB or ZeRO-3. LoRA keeps the frozen base in fp16 and optimises only the adapter, so ~16 GB fits a 24 GB card and QLoRA's 4-bit base brings it under 8 GB. Rejected for this task: full FT (no hardware), QLoRA (0.5B fits fp16 comfortably; QLoRA is the 7B answer), r=8, attention-only adapters, synthetic data (Banking77 is already clean), and the 1.5B model (slower for no better accuracy).

Task 2 — retrieval from scratch

Corpus: NIST AI RMF 1.0 (NIST AI 100-1), 48 pages and 105,949 characters of public-domain text. No LangChain, no LlamaIndex — PyMuPDF for text, NumPy for the maths. I wrote 15 questions myself and then verified every gold quote is a verbatim substring of the page it points to; that check caught two questions where I had misremembered the wording.

Pipeline: extract page by page → chunk inside page boundaries (116 chunks at 256 tokens, 62 at 512, 64-token overlap) → BAAI/bge-small-en-v1.5 (384-d) → cosine top-5. BM25 uses rank_bm25 over the same chunks; the hybrid is reciprocal rank fusion of both lists.

512-token chunks beat 256 on dense recall (0.733 vs 0.667) because the 256 splits cut answers across boundaries. Page-hit@5 moves the other way (0.800 → 0.733), but that is not a trend: three questions flip and they roughly cancel — q7 and q11 lose the gold page at 512, q4 gains it. With n=15 one question is 6.7 pp, so recall@5 is the number I trust. BM25 is flat at 0.800 for both sizes: exact terms survive a chunk boundary in a way that a 384-d vector does not.

Why BM25 wins here. The questions quote the document's own vocabulary — GOVERN, MAP, MEASURE, "risk tolerance". BM25's IDF automatically upweights exactly those rare tokens, while the dense model blurs them into a generic "AI governance" neighbourhood. The honest caveat: I wrote the questions after reading the corpus, so they are partly term-anchored, which flatters BM25. A fair version of this test adds paraphrases.

Two failures. q9: the same definition is printed on pages 8 and 17; gold is page 8, both retrievers return page 17. The content is right and the label is wrong — a gold ambiguity, not a retrieval miss. q15: asks for a procedure; the top dense hit is a topic paragraph with the same nouns. BM25 ranks the gold chunk first because the procedure section repeats the exact term — the case that shows lexical matching is not just a baseline.

BM25 in one paragraph. Score a chunk by summing, over query terms, an IDF weight times a saturated term frequency, with a length penalty: score = Σ IDF(t)·tf(t,d)(k1+1) / (tf(t,d)+k1(1−b+b·|d|/avgdl)). k1 (1.2–2.0) controls saturation, b (0.75) controls length normalisation. Strengths: rare jargon, zero training, an index you can build in milliseconds. Weaknesses: no synonyms, no word order, no negation.

Re-rankers. A cross-encoder reads (query, chunk) together, so it sees order and negation that a bag of words and a single vector both miss. Run it on the top 20 only: 20 short forward passes, ~50–100 ms on a GPU, and it fixes precisely the q15 failure by scoring the relationship rather than the overlap. I left it out because 15 questions cannot measure its gain, and the brief asked for analysis of the option, not a bigger stack.

Task 3 — local model, two quantisation settings

llama.cpp b12465 (CPU build), Qwen2.5-3B-Instruct in GGUF, Q4_K_M vs Q8_0, 4 threads on an i3-1115G4 (2 cores / 4 threads), 8,192-token context, temperature 0, seed 1234. Ten prompts, each with a checkable answer rather than a vibe: JSON extraction, arithmetic, a two-sentence summary, code that must parse, factual recall, a refusal, Hindi, classification, a syllogism, and long-context recall.

The tok/s spread is real, not noise I am hiding: on two physical cores that are also running Windows and an IDE, prompts ranged from 0.74 to 10.29 tok/s. The median is the honest headline; the mean (7.41) is dragged down by the Hindi prompt. Q4_K_M passed 9/10 — the one miss was the Hindi answer, which was correct but one sentence where the prompt demanded two. That is instruction-following, not knowledge: exactly the surface constraint a tighter quantisation is expected to degrade first.

KV cache. Every generated token attends to the keys and values of every earlier token at every layer. Those vectors never change, so they are cached instead of recomputed. Size is set by the architecture, not the weights: 2 (K,V) × layers × kv_heads × head_dim × bytes × context. For this 3B model that is 2 × 36 × 2 × 128 × 2 = 36 KiB per token, so 8,192 tokens costs 288 MiB. Grouped-query attention (16 query heads share 2 KV heads) cuts it 8× versus full multi-head. It is per sequence: 20 users means 20×, which is why a serving plan is a KV-budget plan, not a weights plan.

Quantisation. fp16 stores 2 bytes per weight, so 3.09B parameters would need ~6.2 GB. Q8_0 keeps 8 bits plus one scale per 32-weight block (~8.5 bits/weight) → 3.37 GB measured. Q4_K_M mixes 4-bit and 6-bit tensors with per-block scales and minimums → 1.96 GB, ~5.2 effective bits/weight. The saving is close to linear in bits, with a small overhead for block metadata. Crucially, quantisation changes weights only: the KV cache and the activations are separate allocations, so the KV number is identical for both models, and you can quantise the KV cache independently (--cache-type-k q8_0 --cache-type-v q8_0) to halve it. Q8 is near-lossless; Q4 is where long-tail knowledge and surface constraints start to wobble. Decoding is bandwidth-bound, so reading 2 GB per token is faster than reading 3.4 GB — Q4 should also win on speed.

20 concurrent users on one 24 GB GPU

The 3B model is the wrong size for this question, so the plan uses Qwen2.5-7B-Instruct at Q4_K_M (~4.1 GiB weights). Qwen2.5-7B has 28 layers, 4 KV heads, head_dim 128: 2 × 28 × 4 × 128 × 2 = 56 KiB/token; an 8,192-token context is 448 MiB per user; 20 users is 8.75 GiB. Add ~2 GiB for compute buffers, CUDA context and fragmentation: ~15 GiB of 24, with 9 GiB spare. With an 8-bit KV cache the KV term halves to 4.4 GiB and the total drops to ~10.5 GiB, which is the configuration I would actually ship.

Serve with llama-server -np 20 -c 163840 --cache-type-k q8_0 --cache-type-v q8_0 --cont-batching: the context is split across slots, so each of the 20 slots gets 8,192 tokens, and llama.cpp reserves that space up front — the number above is a hard allocation, not a worst case. If traffic is bursty short chats with occasional long ones, vLLM with PagedAttention is the better fit because it allocates KV in blocks on demand and idle sessions cost almost nothing. Throughput on a 4090-class card is roughly 60–80 tok/s for a single stream and 400–600 tok/s aggregate with continuous batching, so 20 active users see ~20–30 tok/s each, about reading speed; an A10-class card halves that. Ship with an admission cap of 20 active sequences, a per-request max_tokens so one user cannot hold a slot for minutes, prefix caching for the shared system prompt, and a queue — letting the batch grow instead just makes everyone slow.

What I would do next, and what I cannot claim

The 2-core laptop is the binding constraint in Task 3: the first forward pass after loading took 339 s of cold page-cache paging, which is why the runner does an explicit warm-up and excludes it. Ten prompts is a smoke test, not a benchmark — enough to catch a broken quantisation, not enough to rank two good ones. Task 2's n=15 means one question moves recall by 6.7 pp, and my questions are term-anchored. With more time: paraphrase the Task 2 questions and add a cross-encoder re-ranker; sweep LoRA r on Task 1 instead of arguing from parameter counts; and run Task 3 on a machine where Q8_0 (3.4 GB) is not fighting Windows for 7.7 GB of RAM.
